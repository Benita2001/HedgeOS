# HedgeOS — The Four Distinct Integration Surfaces

This document exists because it is easy to conflate these and easy to overstate what's actually connected to what. Every claim here matches the verified state as of 2026-09-08 19:30 UTC — corrected in this pass after checkpoints 9–11 (real live adapter, real preflight, real credential installed) made an earlier version of this document stale.

## 1. Binance Agent OS MCP server (`agent.binance.com/mcp/agentic`)
Binance's own MCP server. Requires interactive browser OAuth consent — confirmed via official docs to have **no headless, service-account, or refresh-token authentication method**. Compatible clients are explicitly interactive tools (Claude, Claude Code, Codex, ChatGPT, VS Code), not unattended servers.

**Status**: connected and verified across multiple sessions this project. Real read-only tool calls made and captured verbatim, e.g. `spot_tickerPrice(NVDABUSDT)`, `futures_usds_symbolPriceTicker(NVDAUSDT)`, `futures_usds_exchangeInformation` (contract identity: `contractType: "TRADIFI_PERPETUAL"`, `underlyingType: "EQUITY"`, `underlyingSubType: ["TradFi"]`).

**Important account-context finding (verified this session via `wallet_getApiKeyPermission`, real call)**: the credential behind this Agent OS connection has `enableFutures: false` — **it cannot read or trade Futures at all**, only `enableSpotAndMarginTrading: true`. This is a genuinely different account/credential from the main REST account used for the real live preflight in checkpoint 10 (which had `enableFutures: true`, confirmed then). **This is exactly the separation the project has documented since `EXECUTION_ROUTE_DECISION.md`**: Agent OS's real, usable role here is bStock/Spot-side market data and (if ever authorized) Spot trading; the hedge/Futures leg has never been reachable through this Agent OS connection and is not claimed to be. Any reconciliation of a real Futures order must use the main REST-authenticated account (`src/binance/liveExecution.ts`), never Agent OS's Futures reads, because for this project's actual credentials they are not the same account.

Session-bound: this connection requires this session's own interactive OAuth consent and does not persist to any other process. Nothing in the persistent worker's runtime import graph calls it — its role is strictly **operator-side**, formalized in `docs/AGENT_OS_OPERATOR_WORKFLOW.md`: an interactive session obtains source-attributed observations from Agent OS and passes them to HedgeOS's own `preview_with_agent_os_observations` MCP tool (surface 2), which independently re-verifies instrument identity and price against public REST before any sizing occurs — the Agent OS observation itself never reaches the sizing engine.

## 2. HedgeOS's own operator MCP server (`src/mcp/server.ts`)
Built by this project, unrelated to Binance's server beyond using the same MCP protocol. Exposes the **running persistent service's** state (strategies, positions, receipts, risk alerts) and a set of paper-mode actions (create/pause/resume/trigger/preview/funding-check) to any MCP client. Verified working from both **Claude Code** (smoke-tested, `scripts/mcp-smoke-test.ts`) and **Codex** (real `codex exec` session, real tool calls, this project's own history).

**Status**: real, deployed (the read/paper-mode tool set), verified — see `PROGRESS_LOG.md`. `trigger_due_cycle` goes through the exact same idempotent claim path as the scheduler itself. `preview_with_agent_os_observations` and `check_funding_readiness` are the two tools that accept operator-supplied context (Agent OS observations; the operator's own account credentials, respectively) — both cross-check against HedgeOS's own live discovery/sizing rather than trusting the input.

## 3. Public Binance REST (`api.binance.com`, `fapi.binance.com`)
What the persistent worker actually uses for every market observation: symbol discovery (`src/binance/client.ts`), live prices, contract filters. No authentication, no session, no OAuth to expire — which is exactly why it's the only viable foundation for something that must run unattended for weeks.

**Status**: real, live, this is what every paper execution in this project has actually been priced against.

## 4. Live Futures/Spot REST execution adapter (`src/binance/liveExecution.ts`, `liveRequests.ts`, `liveHttp.ts`)
Real, authenticated, direct HMAC-signed REST (not Agent OS, not MCP) — the same underlying API a live Agent OS trade tool would itself ultimately call. Idempotent order placement with ambiguous-outcome recovery, leverage/margin verification against actual account state before an order is sent, independent trade-data reconciliation (never trusts an order-placement response alone), and a stock-filled/hedge-throws safety net so a real fill's record can't be lost.

**Status**: real code, integration-tested (`tests/liveExecution.test.ts`, `tests/liveLifecycle.test.ts` — mocked HTTP client, zero real network calls in tests). Fail-closed behind a 4-condition gate (`assertLiveTradingGate`) that nothing in this repo's default config sets. **A real credential now exists** — installed by the account owner directly on the VPS, in a separate protected file (`/opt/hedgeos/secrets/live-preflight.env`, mode 600, never in this repo, never in chat) — and was used for one real, authenticated, **read-only** preflight (checkpoint 10: 10/10 checks passed). **No real order has ever been placed.** The two live-mode confirmation env vars (`HEDGEOS_LIVE_TRADING_CONFIRMED`, `HEDGEOS_LIVE_CHECKLIST_COMPLETE`) remain unset everywhere.

## Why this separation is the honest design, not a workaround
An agent that must run continuously and independently of any laptop or chat session cannot be built on an authentication method that has no headless mode — that's a fact about Agent OS today, not a limitation HedgeOS invented. The persistent service (surfaces 3 and, once authorized, 4) is deliberately Agent-OS-independent. Agent OS's real, supported role in this architecture is surface 1: an optional, session-bound, **Spot-side-only** enhancement to the **operator** experience, layered on top of — never underneath — the autonomous service. **The entire worker is not, and should not be described as, "Agent OS-native"** — its actual implementation (surface 3, public REST) proves otherwise; Agent OS is an operator convenience, not a runtime dependency.
